เส้นทางที่ 2 — PB Process (Classic):
- อ่านรหัสกระบวนการ (process code) ที่ส่งเป็นพารามิเตอร์ตัวแรกใน
  `WebUtil.runProcessingExtend("<CODE>", ...)` หรือ `WebUtil.runProcessing("<CODE>", ...)`
  จากโค้ด C# จริง
- เปิดหาไฟล์ dispatcher ใต้ path ที่เกี่ยวข้อง (runProcessingExtend → Path PB
  Process Extend, runProcessing → Path PB Process Core) — ไฟล์
  dispatcher มักตั้งชื่อตามโมดูล/ระบบ (เช่น `n_cst_pbprocess_<ชื่อโมดูล>.sru`)
  ให้ค้นหาไฟล์ `.sru` ที่มีบรรทัด `case "<CODE>"` ตรงกับรหัสที่พบ
- เมื่อเจอ case ให้ดูว่า instantiate object อะไร (เช่น `create n_cst_proc_xxx`)
  แล้วเรียก entry function ใด (เช่น `.of_xxx()`) — นี่คือจุดเริ่มต้นให้ไล่อ่านต่อ
- ถ้าหา dispatcher ไม่เจอ หรือหาบรรทัด `case` ที่ตรงกับรหัสไม่เจอ หรือเจอ
  dispatcher ที่เป็นไปได้มากกว่า 1 ไฟล์ ห้ามเดา ให้บันทึกเป็นข้อสังเกตในหัวข้อ 10
  แล้วบันทึกเฉพาะจุดเชื่อมโยง (หัวข้อ 7) ตามข้อมูลที่มีจากฝั่ง C# เท่านั้น
- **⚠ กฎสำคัญเรื่องไฟล์ `.pbl`**: ห้ามสรุปว่าไฟล์ `.pbl` "เป็น binary อ่านไม่ได้"
  จากผลคำสั่งตรวจชนิดไฟล์ (เช่น `file`) เพียงอย่างเดียว — PowerBuilder library
  ที่ compile แล้วมักยังฝัง **source code ต้นฉบับเป็น UTF-16LE text ไว้ภายใน
  ไฟล์ไบนารี** เช่นเดียวกับไฟล์ `.sru`/`.srw` ก่อนสรุปว่าอ่านไม่ได้ ให้ลอง
  extract ข้อความอ่านได้จากไฟล์ก่อนเสมอ ด้วยวิธีใดวิธีหนึ่ง:
  - เขียนสคริปต์ (Python) อ่านไฟล์แบบ binary แล้วหา pattern ตัวอักษร ASCII/Thai
    สลับกับ byte `0x00` (regex ประมาณ `(?:[\x20-\x7e]\x00){6,}` แล้ว decode ด้วย
    `utf-16le`) เพื่อดึงบล็อกข้อความที่อ่านได้ออกมา
  - หรือ `grep -a -P` ด้วย pattern ตัวอักษรคั่น null byte (เช่น `o\x00f\x00_\x00...`)
    เพื่อค้นชื่อฟังก์ชัน/SQL ที่ต้องการ

  "ลึกไม่เกิน 1 ชั้น" แบบ Dialog เพราะฟังก์ชันย่อยในอ็อบเจ็กต์เดียวกันคือ
  เนื้อหาเดียวกันของกระบวนการนี้) แต่ถ้าอ็อบเจ็กต์นี้เรียกออกไปหาอ็อบเจ็กต์/
  ไลบรารี/บริการอื่นต่ออีกทอดหนึ่ง ให้บันทึกเป็นจุดเชื่อมโยง (หัวข้อ 7) แล้ว
  หยุด ไม่ไล่อ่านต่อ
- **ตรวจคุณภาพก่อนใช้ (บังคับ):** ก่อนนำเนื้อหาที่แกะได้ไปเขียนเอกสาร ให้ตรวจ
  2 อย่างนี้เสมอ ขาดข้อใดข้อหนึ่งไม่ได้:
  1. เนื้อหาที่ได้เป็นโค้ด PowerScript ที่สมเหตุสมผลจริง (มีโครงสร้าง
     function/end function ครบ ไม่มีอักขระแปลกปนจนอ่านไม่รู้เรื่อง)
  2. **บรรทัด signature แรกของโค้ดที่แกะได้ ต้องมีชื่อฟังก์ชันตรงกับชื่อที่
     กำลัง trace อยู่เป๊ะๆ** (เช่น กำลังหา `of_caldivloanpermiss` แต่โค้ดที่ได้
     ขึ้นต้นด้วย `public function ... of_initservice (...)` = ผิดฟังก์ชัน
     ห้ามใช้เด็ดขาด)
  - **⚠ ข้อผิดพลาดที่เคยเกิดจริง**: ไฟล์ `.sru` ของ GCOOP เกือบทุกไฟล์มีบล็อก
    `forward prototypes ... end prototypes` อยู่ต้นไฟล์ ซึ่งประกาศชื่อฟังก์ชัน
    **ทุกตัว**ในอ็อบเจ็กต์ไว้ล่วงหน้าแบบไม่มี body ถ้าค้นหาชื่อฟังก์ชันแบบง่ายๆ
    (หาชื่อเจอที่ไหนก่อนก็ลากยาวไปจนถึง `end function` ตัวถัดไป) จะไป match
    กับชื่อในบล็อก prototype นี้แทน แล้วลากคัดลอกโค้ดของฟังก์ชันแรกที่
    implement จริงหลัง `end prototypes` (มักเป็น `of_initservice`) มาแปะผิด
    เป็น "source code" ของทุกฟังก์ชันที่ trace — วิธีป้องกัน: (ก) ข้ามบล็อก
    `forward prototypes...end prototypes` ทั้งหมดก่อนค้นหาเสมอ ให้ค้นหาเฉพาะ
    ส่วนหลัง `end prototypes` เท่านั้น (ข) ใช้ข้อ 2 ด้านบนเป็นตัวเช็คสุดท้าย
    ทุกครั้งไม่ว่าจะค้นหาด้วยวิธีใด (grep, สคริปต์ที่เขียนเอง, หรืออ่านด้วยตา)
  ถ้าเนื้อหาที่แกะได้ไม่ผ่านการเช็คข้อใดข้อหนึ่งข้างต้น **ห้ามใช้และห้ามเดาเติม
  ส่วนที่ขาด** ให้ถอยไปบันทึกเฉพาะจุดเชื่อมโยง (หัวข้อ 7) ตามข้อมูลที่มีจากฝั่ง
  C# แทน พร้อมบันทึกในหัวข้อ 10 ว่าไม่สามารถแกะเนื้อหากระบวนการนี้ได้สมบูรณ์
- **Dynamic SQL:** ถ้าพบการประกอบคำสั่ง SQL จากการต่อ string ตัวแปร (เช่น
  `execute immediate :ls_sql`) ห้ามเดาข้อความ SQL ที่สมบูรณ์ถ้าไม่เห็นค่า
  ตัวแปรที่นำมาต่อครบทุกจุด ให้บันทึกเท่าที่เห็นจริงและตั้งข้อสังเกตในหัวข้อ 10
- **พฤติกรรมแบบ Batch:** PB Process ในระบบนี้ทำงานจนจบกระบวนการแล้วรายงาน
  สถานะความคืบหน้ากลับผ่านตารางในฐานข้อมูล (ไม่ใช่ synchronous call ที่รอ
  ผลกลับทันทีแบบ Service) เมื่อพบรูปแบบนี้ ให้ตรวจโค้ด C# ของหน้าจอด้วยว่า
  มีการอ่านตารางสถานะนั้นมาแสดงผลความคืบหน้าหรือไม่ ถ้ามี ให้อธิบายไว้ใน
  หัวข้อ 2 (ลำดับขั้นตอนการทำงาน) และนำตารางสถานะนั้นไปลงหัวข้อ 9 ด้วย

ระบบเลขรหัสสำหรับฟังก์ชัน/Rule ทั้งหมด (ใช้อ้างอิงในหัวข้อ 4/5/9):
- ฟังก์ชัน: หน้าจอหลัก = 1, 2, 3, ... / หน้าจอย่อยตัวที่ n = `D{n}-1`, `D{n}-2`, ... /
  PB Service ตัวที่ n = `S{n}-1`, ... / PB Process ตัวที่ n = `P{n}-1`, ...
- Rule: หน้าจอหลัก = `BR-01`, `BR-02`, ... / หน้าจอย่อยตัวที่ n = `BR-D{n}-01`, ... /
  PB Service = `BR-S{n}-01`, ... / PB Process = `BR-P{n}-01`, ...
- เรียงลำดับเสมอ: หน้าจอหลักก่อน → หน้าจอย่อยแต่ละตัวตามลำดับ D# → PB Service/
  Process แต่ละตัวตามลำดับ S#/P# (ห้ามแยกตาราง)
- เนื้อหาที่มาจาก PB Service/Process **ต้องตั้ง needs_human_review: true เสมอ**
  ในหัวข้อ 10 (ความเสี่ยงคลาดเคลื่อนสูงกว่าอ่านโค้ด C# ปกติ เพราะต้องค้นหา
  object/function เองจากรหัสกระบวนการ) ถ้าแกะเนื้อหาไม่สำเร็จหรือไม่สมบูรณ์
  ต้องบันทึกเป็นข้อเท็จจริงของระบบงาน เช่น "การคำนวณค่าปรับดำเนินการโดยบริการ
  คำนวณกลาง เอกสารฉบับนี้จึงไม่ครอบคลุมสูตรคำนวณดังกล่าว" (ห้ามเขียนถึงขอบเขต
  การอ่านโค้ดหรือปัญหาการแกะไฟล์ของผู้จัดทำ)

## 4. คุณสมบัติและฟังก์ชัน
**ไม่ใช่ตาราง** — เขียนแต่ละฟังก์ชันเป็นรายการเรียงลำดับตามระบบเลขรหัสในหัวข้อ
PB SOURCE READING (หน้าจอหลักก่อน 1, 2, 3, ... แล้วต่อด้วยหน้าจอย่อยแต่ละตัว
D1-1, D1-2, ... แล้ว D2-1, ...) เพื่อให้ source code อยู่ติดกับฟังก์ชันที่มัน
อธิบายทันที ไม่ลอยแยกไปอยู่ท้ายเอกสาร ใช้รูปแบบนี้เป๊ะๆ ต่อ 1 ฟังก์ชัน:

```
#### <รหัส>. <ชื่อฟังก์ชัน>
<คำอธิบายว่าฟังก์ชันนี้ทำอะไร>

*อ้างอิงไฟล์:method* -> `<ไฟล์>:<method>`

<details>
<summary>📄 Source Code</summary>

​```<ภาษาของไฟล์ต้นทาง เช่น csharp, powerscript>
<โค้ดจริงตามที่อ่าน ไม่ตัดต่อ/สรุป — ดูกฎ "Source Code ของรายการที่มาจาก PB"
ด้านล่างสำหรับรหัส S#/P#>
​```
</details>

---
```

ต้องมี block นี้ครบทุกรายการ เรียงลำดับตามระบบเลขรหัส ห้ามข้ามรายการใด

**⚠ Source Code ของรายการที่มาจาก PB (รหัส S#/P#) — กฎสำคัญที่พลาดบ่อยที่สุด**:
ต้องเป็นเนื้อหาฟังก์ชัน PowerScript **จริง** จาก `.sru`/`.pbl` ที่ trace ได้ตาม
หัวข้อ PB SOURCE READING (เส้นทางที่ 1/2) — พบมาแล้วว่า agent ทำผิด 2 แบบ
ต้องระวังทั้งคู่:
1. **แนบแค่บรรทัดเรียกจากฝั่ง C#** (เช่น `wcf.NLoan.of_xxx(...)`) ซึ่งซ้ำกับที่
   แสดงในคำอธิบาย/อ้างอิงไฟล์ไปแล้ว ไม่มีประโยชน์เพิ่ม
2. **กุ (fabricate) stub function ปลอมขึ้นมาเอง** เมื่อ trace เนื้อหาจริงไม่สำเร็จ
   แทนที่จะยอมรับว่าแกะไม่ได้ — ตัวอย่างจริงที่เคยเกิดขึ้น (ห้ามทำแบบนี้เด็ดขาด):
   ```powerbuilder
   public function integer of_getcollpermiss (...) throws Exception;
   return 1
   end function
   ```
   ```powerbuilder
   public function decimal of_getcollusecontamt (...) throws Exception;
   return ldc_collusecont
   end function
   ```
   สังเกตว่าตัวอย่างที่สองใช้ตัวแปร `ldc_collusecont` ใน return โดยไม่เคยประกาศ/
   คำนวณเลยในโค้ดที่แสดง — เป็นลายเซ็นของการเดา ไม่ใช่โค้ดจริง (โค้ด PowerScript
   จริงคอมไพล์ไม่ผ่านถ้าใช้ตัวแปรที่ไม่ได้ประกาศ)

**วิธีตรวจจับก่อนใส่ในเอกสาร**: ถ้าคำอธิบายฟังก์ชัน/Rule บอกว่ามี logic คำนวณ/
ตรวจสอบที่ซับซ้อน (เช่น "คำนวณสิทธิ์และวงเงินค้ำประกัน") แต่เนื้อหาโค้ดที่แกะได้
มีแค่ signature + `return <ค่าคงที่หรือตัวแปรเดียว>` โดยไม่มี logic ประกอบ (ไม่มี
query, ไม่มี if/loop, ไม่มีการประกาศ/คำนวณตัวแปรที่ใช้ใน return) ให้ถือว่าเป็น
การเดา **ห้ามใช้เด็ดขาด** — ให้เขียนในกล่อง source code ว่า "ไม่สามารถแนบ
source code ได้ — แกะเนื้อหาจาก .pbl/.sru ไม่สำเร็จ" แทน (ข้อยกเว้น: ฟังก์ชันที่
คำอธิบายบอกไว้ชัดว่าง่ายจริงๆ เช่น "คืนค่าวันที่ที่รับเข้ามาตรงๆ" ซึ่ง body สั้นได้
ตามจริง — ต้องพิจารณาความสอดคล้องระหว่างคำอธิบายกับความยาว/ความซับซ้อนของโค้ด)

CONSTRAINTS:
- **ห้ามเขียน/แต่ง source code ขึ้นมาเองเด็ดขาด ไม่ว่าภาษาใดก็ตาม** (C#, SQL,
  PowerScript, JavaScript ฯลฯ) — ทุก code snippet ที่ปรากฏในเอกสารนี้ ไม่ว่าจะ
  อยู่ในกล่อง collapsible (หัวข้อ 4/5) หรือที่อื่นใด ต้อง copy มาจากไฟล์ที่เปิด
  อ่านจริงเท่านั้น คำ **บรรยาย**ว่าโค้ดทำอะไร (business rule, สูตรคำนวณเป็น
  ข้อความ) อนุมานจากโค้ดที่อ่านได้ตามปกติ แต่ตัว **code block เอง** ห้ามพิมพ์
  ขึ้นเองแม้บรรทัดเดียว แม้จะดูสมเหตุสมผล/น่าจะถูกต้องแค่ไหนก็ตาม ถ้าไม่มีโค้ด
  จริงให้แสดง ห้ามใส่โค้ดที่แต่งเอง (รวมถึง stub เช่น signature จริงแต่ body
  เดา) ให้เขียนข้อความตรงๆ แทนว่า "ไม่สามารถแนบ source code ได้ — [เหตุผล]"
  (ดูตัวอย่าง anti-pattern จริงที่เคยเกิดขึ้นในกฎของหัวข้อ 4)
- ห้ามสร้างข้อมูลที่ไม่มีหลักฐานในโค้ด แม้จะดูสมเหตุสมผลก็ตาม

- ห้ามเปิดอ่านไฟล์ PowerBuilder ใดๆ ที่ไม่พบหลักฐานการเรียกจริงในโค้ด C#

  ไม่สำเร็จหรือดูไม่สมบูรณ์เด็ดขาด (ดูหัวข้อ PB SOURCE READING) — ให้บันทึก
  เฉพาะสิ่งที่ยืนยันได้จริงจากซอร์สที่อ่าน
- ห้ามเขียนสูตรคำนวณเป็น LaTeX (เช่น $...$, \sum, \text{}, \times) ให้เขียน
  เป็นข้อความ/สัญลักษณ์ธรรมดาแทน เช่น:
  ผิด:  $\text{sum} = \sum_{i=1}^{12} (\text{PID}[i-1] \times (14 - i))$
  ถูก:  sum = SUM(PID[i-1] × (14-i), i=1..12)
  ต้องเขียนแบบเดียวกันทุกตัวอักษรทั้งในไฟล์ .md และ .html
- Source code แบบ collapsible ในหัวข้อ 4/5 แนบเฉพาะ snippet ของฟังก์ชัน/Rule
  รายการนั้นๆ เท่านั้น ห้ามแนบทั้งไฟล์ทั้งฉบับ

  trace ได้เท่านั้น — ห้ามแนบแค่บรรทัดเรียกจากฝั่ง C#, และห้ามกุ (fabricate)

  การเดาที่ CONSTRAINTS ข้อแรกห้ามไว้แล้ว แต่ระบุซ้ำเพราะเป็นจุดที่เคยพลาดจริง —

  trace ไม่สำเร็จให้เขียนตรงๆ ว่า "ไม่สามารถแนบ source code ได้" แทนการแนบ
